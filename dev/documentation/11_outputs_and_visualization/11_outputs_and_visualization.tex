\section{Persisted Raw Data vs. Presentation Outputs}

The project now distinguishes between:
\begin{itemize}[leftmargin=2em]
    \item \textbf{persisted raw MAPF data} under \texttt{dev/raw\_mapf\_data/<map\_type>/},
    \item \textbf{presentation outputs} under \texttt{dev/outputs/<map\_type>/}.
\end{itemize}

The raw payload is branch-local and survives across later runs. It is replaced only when \texttt{recompute\_MAPF=True}. The presentation outputs can then be regenerated from that saved raw payload without rerunning the expensive solver stage.

The active output manager creates the following presentation-output subfolders:
\begin{itemize}[leftmargin=2em]
    \item \texttt{metadata},
    \item \texttt{records},
    \item \texttt{aggregates},
    \item \texttt{graphs},
    \item \texttt{logs},
    \item \texttt{visualizations}.
\end{itemize}

\section{Structured Files}

When \texttt{to\_generate="graphs\_and\_data"}, the most important regenerated structured outputs are:
\begin{itemize}[leftmargin=2em]
    \item \texttt{metadata/branch\_spec.json},
    \item \texttt{metadata/branch\_stop\_summary.json},
    \item \texttt{metadata/shared\_dynamic\_state.json} for dynamic branches,
    \item \texttt{records/run\_configurations.json} and \texttt{.csv},
    \item \texttt{records/run\_records.json} and \texttt{.csv},
    \item \texttt{aggregates/condition\_summary.json} and \texttt{.csv}.
\end{itemize}

The solver update makes two of those files more informative:
\begin{itemize}[leftmargin=2em]
    \item \texttt{branch\_spec.json} now records the effective solver family metadata for the whole branch run, including the active branch's ECBS bound when relevant,
    \item \texttt{run\_records.json}/\texttt{.csv} now record per-run solver metadata such as CBS vs.\ ECBS and the active suboptimality factor when ECBS is enabled.
\end{itemize}


\section{Logging Behavior}

The experiment logger writes each line both to the branch log file and to stdout immediately. In practical terms, the periodic solver progress lines such as the 5-second classical/cyclic progress reports should now appear live during long runs instead of being buffered and dumped all at once later. The condition header now prints as \texttt{Condition n} rather than \texttt{Condition n/(total conditions)}, and paired sampling attempts are separated by a blank line for readability.

\section{Generation Modes}

The top-level manual control now has three modes:
\begin{itemize}[leftmargin=2em]
    \item \texttt{to\_generate="graphs\_and\_data"}: regenerate structured files and metric graphs from the saved raw payload,
    \item \texttt{to\_generate="visualization"}: regenerate Pillow visualization frames only,
    \item \texttt{to\_generate="nothing"}: do not regenerate presentation artifacts in that run.
\end{itemize}

Because the project now treats graphs/data and Pillow frames as separate artifact families, one family may intentionally remain older than the other until the user chooses to regenerate it.

\section{Graphs}

Each accepted condition can contribute to up to three graphs:
\begin{itemize}[leftmargin=2em]
    \item average halted computation time vs.\ agent number,
    \item average conflicts at halt vs.\ agent number,
    \item average path length vs.\ agent number.
\end{itemize}

Path-length graphs are enabled through the branch specification and currently remain enabled for all branches.

\section{How Aggregates Are Computed}

For a reported condition:
\begin{itemize}[leftmargin=2em]
    \item halted time is averaged over counted runs,
    \item conflicts at halt are averaged over counted runs,
    \item average path length is averaged only over successful runs.
\end{itemize}

This means unfinished runs still influence the first two metrics but not path length.

\section{Pillow Rendering Contract}

When a run is selected for visualization, the renderer writes:
\begin{itemize}[leftmargin=2em]
    \item \texttt{config\_000}: obstacle-only view,
    \item \texttt{config\_001}: showcase view with transitions,
    \item \texttt{config\_002}: setup view with agents and targets,
    \item \texttt{frame\_000}, \texttt{frame\_001}, \dots: the actual solution timeline.
\end{itemize}

\section{Visualization Selection Policy}

When \texttt{to\_generate="visualization"}, visualization selection is controlled by the current values in \texttt{master\_config.py}:
\begin{itemize}[leftmargin=2em]
    \item \texttt{num\_last\_runs\_to\_visualize},
    \item \texttt{require\_jointly\_successful\_mappings}.
\end{itemize}

As a result, changing only these two selection controls no longer requires a fresh MAPF solve. The renderer reuses the persisted raw payload for the selected branch and applies the \emph{current} visualization-selection settings when deciding which successful runs to render.

\subsection{Joint Mode}

If joint success is required, the code selects the last \(n\) run configurations for which both mappings were successful on the same paired configuration. This selection now follows the current \texttt{require\_jointly\_successful\_mappings} value rather than the persisted value stored with the raw MAPF payload.

\subsection{Independent Mode}

If joint success is not required, the code independently selects:
\begin{itemize}[leftmargin=2em]
    \item the last \(n\) successful classical runs,
    \item the last \(n\) successful cyclic runs.
\end{itemize}

\section{Dynamic Visualization Detail}

For dynamic branches, setup frames are rendered from a static setup map derived from the branch's static matrix, while execution frames are rendered against the time-varying loop itself.

\section{Why the Output Shape Matters}

The JSON/CSV outputs are not just byproducts. They are effectively the machine-readable record of the experiment. Any update that changes naming, folder layout, or meaning of those files should be treated as a contract change, not a harmless refactor.
