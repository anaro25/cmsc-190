\section{Persisted Raw Data vs. Presentation Outputs}

The project now distinguishes between:
\begin{itemize}[leftmargin=2em]
    \item \textbf{persisted raw MAPF data} under \texttt{dev/outputs/raw\_mapf\_files/<map\_type>/},
    \item \textbf{presentation outputs} under \texttt{dev/outputs/<map\_type>/}.
\end{itemize}

The raw MAPF store is branch-local and survives across later runs. It is replaced only when \texttt{to\_generate="raw\_data"}. The presentation outputs can then be regenerated from that saved raw data without rerunning the expensive solver stage. Older branch-local roots that still live under \texttt{dev/raw\_mapf\_data/<map\_type>/} or \texttt{dev/raw\_mapf\_files/<map\_type>/} are migrated automatically into the new \texttt{outputs/raw\_mapf\_files} location when the branch is loaded.

The persisted raw-data tree is intentionally split rather than packed into one giant pickle. Each branch root now contains a manifest and metadata files at the top level, plus one condition subfolder per reported agent number. Inside each condition folder, the aggregate summary, retained run configurations, retained run records, and successful visualization candidates are stored separately. This keeps larger experiment ranges much easier to inspect and replace.

The active output manager still uses the same presentation-output families:
\begin{itemize}[leftmargin=2em]
    \item \texttt{metadata},
    \item \texttt{records},
    \item \texttt{aggregates},
    \item \texttt{graphs},
    \item \texttt{logs},
    \item \texttt{visualizations}.
\end{itemize}
However, the presentation-output tree is now \emph{latest-only}. Each purpose keeps one current copy and a newer run overwrites that same location instead of creating a fresh \texttt{execution\_...} folder. A typical branch output root now contains paths such as:
\begin{lstlisting}
dev/outputs/<map_type>/
    logs/
        raw_data/
            experiment.log
        graphs/
            experiment.log
        visualization/
            experiment.log
    metadata/
        graphs/
            branch_spec.json
            graph_generation_branch_spec.json
            branch_stop_summary.json
            shared_dynamic_state.json         # dynamic branches only
        visualization/
            visualization_selection_summary.json
    records/
        graphs/
            run_configurations.json
            run_configurations.csv
            run_records.json
            run_records.csv
    aggregates/
        graphs/
            condition_summary.json
            condition_summary.csv
    graphs/
        graphs/
            ...
    visualizations/
        jointly_successful/
        independently_successful/
\end{lstlisting}

\subsection{Persisted Raw-Data Layout}
A typical persisted raw-data tree for one branch now has the rough form:
\begin{lstlisting}
dev/outputs/raw_mapf_files/<map_type>/
    manifest.json
    raw_mapf_data_summary.json
    metadata/
        branch_spec.json
        branch_stop_summary.json
        dynamic_state.pkl               # dynamic branches only
        dynamic_state_metadata.json     # dynamic branches only
    conditions/
        condition_001__agent_number_010/
            condition_aggregate.json
            run_configurations.json
            run_records.json
            visualization_candidates/
                index.json
                0001__classical__....pkl
                0002__cyclic__....pkl
        ...
\end{lstlisting}
The condition folders contain only the retained reported data for that agent number. The visualization-candidate pickles store the frame-building ingredients for successful runs, while the index file keeps the selection order and filenames explicit.

\section{Structured Files}

When \texttt{to\_generate="graphs"}, the most important regenerated structured outputs inside the current \texttt{graphs/} folders are:
\begin{itemize}[leftmargin=2em]
    \item \texttt{metadata/graphs/branch\_spec.json},
    \item \texttt{metadata/graphs/branch\_stop\_summary.json},
    \item \texttt{metadata/graphs/shared\_dynamic\_state.json} for dynamic branches,
    \item \texttt{records/graphs/run\_configurations.json} and \texttt{.csv},
    \item \texttt{records/graphs/run\_records.json} and \texttt{.csv},
    \item \texttt{aggregates/graphs/condition\_summary.json} and \texttt{.csv}.
\end{itemize}

The solver update makes two of those files more informative:
\begin{itemize}[leftmargin=2em]
    \item \texttt{branch\_spec.json} now records the effective solver family metadata for the whole branch run, including the active branch's ECBS bound when relevant,
    \item \texttt{run\_records.json}/\texttt{.csv} now record per-run solver metadata such as CBS vs.\ ECBS and the active suboptimality factor when ECBS is enabled.
\end{itemize}


\section{Logging Behavior}

The experiment logger writes each line both to the stage-specific log file and to stdout immediately. In practical terms, the periodic solver progress lines such as the 5-second classical/cyclic progress reports should now appear live during long runs instead of being buffered and dumped all at once later. The condition header now prints as \texttt{Condition n} rather than \texttt{Condition n/(total conditions)}, paired sampling attempts are separated by a blank line for readability, and the branch header no longer prints the full long list of planned agent numbers.

\section{Generation Modes}

The top-level manual control now has three modes:
\begin{itemize}[leftmargin=2em]
    \item \texttt{to\_generate="raw\_data"}: recompute and save the raw MAPF solver payload only,
    \item \texttt{to\_generate="graphs"}: regenerate structured files and metric graphs from the saved raw payload,
    \item \texttt{to\_generate="visualization"}: regenerate Pillow visualization frames only.
\end{itemize}

Because the project now treats graphs/data and Pillow frames as separate artifact families, one family may intentionally remain older than the other until the user chooses to regenerate it.

\section{Graphs}

\subsection{Graph X-Axis Domain}

When \texttt{to\_generate="graphs"} is run against already-saved raw MAPF data, the plotted metric values and the x-axis tick labels are both derived from the agent numbers that are actually present in the persisted branch records being graphed. The graphing layer still forces every such x-value to be labeled explicitly, so Matplotlib does not silently skip labels such as showing only \(2,4,6,\dots\).

This keeps regenerated graphs compact: if the current branch domain in \texttt{master\_config.py} extends far beyond the previously computed results, the x-axis no longer stretches across that unused range. Backward compatibility is preserved because older saved raw data remains readable without needing to recompute it under the newer domain.

The plotting layer also computes compact vertical limits from the values that are actually drawn, with a small padding margin above and below the observed range. This avoids large empty regions when values are close while still preventing the extreme points from touching the frame. The runtime-limit reference line is no longer forced into every runtime graph; it is drawn only when at least one plotted runtime value reaches the configured limit.


The updated capacity-search protocol currently writes text-only raw-data and evaluation logs. Graph regeneration is intentionally marked as a later update for the new protocol, because the main output no longer consists of averaged metric curves over a long agent-number progression.

\section{How Detailed Capacity Values Are Reported}

For a reported capacity point:
\begin{itemize}[leftmargin=2em]
    \item halted time is written as the direct run value,
    \item conflicts at halt is written as the direct run value,
    \item total path length is written only when the run is successful.
\end{itemize}

The current main-experiment protocol keeps one successful capacity run per mapping and configuration. Therefore, the detailed logs do not add average lines for the main values.

\section{Pillow Rendering Contract}

When a run is selected for visualization, the renderer writes:
\begin{itemize}[leftmargin=2em]
    \item \texttt{config\_000}: obstacle-only view,
    \item \texttt{config\_001}: showcase view with transitions,
    \item \texttt{config\_002}: setup view with agents and targets,
    \item \texttt{frame\_000}, \texttt{frame\_001}, \dots: the actual solution timeline.
\end{itemize}

\section{Visualization Selection Policy}

When \texttt{to\_generate="visualization"}, visualization selection is controlled by the current values in \texttt{master\_config.py}:
\begin{itemize}[leftmargin=2em]
    \item \texttt{num\_last\_runs\_to\_visualize\_jointly\_successful},
    \item \texttt{num\_last\_runs\_to\_visualize\_independently\_successful}.
\end{itemize}

As a result, changing only these selection controls no longer requires a fresh MAPF solve. The renderer reuses the persisted raw payload for the selected branch and applies the \emph{current} visualization-selection settings when deciding which successful runs to render.

Gray campus regions may be carried separately as render-only visually free vertices. When that semantic mask is present, the visualization pipeline now reconstructs the current gray-mask semantics from the branch image and applies them twice: it passes the visually free vertex set to the renderer and also builds a render-only composite-map copy in which those gray obstacle vertices are temporarily replaced by free-space cells for drawing. This keeps gray campus regions visibly white and open-looking in Pillow outputs while the solver still treats them as non-traversable. Because the reconstruction comes from the current branch image, older persisted raw MAPF stores can still be reused without recomputing solver-stage data.

\subsection{Jointly Successful Variant}

The code selects the last \(n\) run configurations for which both mappings were successful on the same paired configuration and writes them under a dedicated \texttt{jointly\_successful/} folder.

\subsection{Independently Successful Variant}

The code independently selects:
\begin{itemize}[leftmargin=2em]
    \item the last \(n\) successful classical runs,
    \item the last \(n\) successful cyclic runs,
\end{itemize}
and writes them under a dedicated \texttt{independently\_successful/} folder.

Both visualization variants are generated in one visualization-only execution, so the old rerun that flipped a boolean selection mode is no longer needed.


\section{Visualization Logging Granularity}

The visualization-only execution now emits more stopwatch updates while Pillow frames are being generated. The log records elapsed-time milestones after each selected mapping render, and jointly successful selections also record a completion milestone per selected run configuration. This makes long frame-generation stretches easier to monitor from both the terminal and the saved \texttt{experiment.log}. Visualization outputs are written directly under \texttt{visualizations/} rather than under an extra nested \texttt{visualization/} folder.

\section{Dynamic Visualization Detail}

For dynamic branches, setup frames are rendered from a static setup map derived from the branch's static matrix, while execution frames are rendered against the time-varying loop itself.

\section{Why the Output Shape Matters}

The JSON/CSV outputs are not just byproducts. They are effectively the machine-readable record of the experiment. Any update that changes naming, folder layout, or meaning of those files should be treated as a contract change, not a harmless refactor.
