\section{Where to Make Changes First}

When modifying current behavior, the safest order of inspection is:
\begin{enumerate}[leftmargin=2em]
    \item \texttt{master\_config.py},
    \item \texttt{experiments/branch\_specs.py},
    \item \texttt{experiments/study/preparation.py},
    \item \texttt{experiments/study/runtime.py},
    \item \texttt{mapf/agent\_assignment.py},
    \item the relevant solver modules under \texttt{mapf/},
    \item \texttt{experiments/study/orchestrator.py},
    \item \texttt{experiments/study/raw\_data\_store.py} if persisted raw-data behavior changes,
    \item \texttt{experiments/study/aggregation.py}, \texttt{plotting.py}, and \texttt{visualization.py} if outputs also change.
\end{enumerate}

\section{Invariants Worth Preserving}

\subsection{Paired Fairness Contract}
Do not accidentally compare classical and cyclic on different retained configurations for a reported condition. The current project deliberately discards jointly non-viable samples instead.

\subsection{Dynamic Shared-State Contract}
Dynamic branches are meant to share one prepared dynamic environment across the whole branch execution. If that is changed, the meaning of the experiment changes.

\subsection{Status-to-Category Contract}
The runner currently treats:
\begin{itemize}[leftmargin=2em]
    \item \texttt{solved} as successful,
    \item \texttt{bad\_setup\_timeout} as unfinished,
    \item \texttt{no\_solution} as unsolvable.
\end{itemize}
Changing this mapping would change reported metrics and stopping behavior.

\subsection{Campus Semantic Contract}
The campus branches depend on semantic colors, not just thresholding. Any update to campus input processing should preserve the meanings of zone colors, white walkways, and gray regions unless the experiment design itself is intentionally changed.

\subsection{Campus Image Variant Contract}
The campus branches select their source images through the fixed campus image path helper in \texttt{master\_config.py}. If filenames or folder names change, update both the config helper and the recorded branch metadata so it remains obvious which campus layout was actually run.

\subsection{Assignment Cardinality Contract}
Dispersed and clustered goal modes are one-to-one MAPF setups. The \texttt{single} goal mode is the explicit target-only many-to-one setup, where all agents share one literal target cell. Do not use \texttt{single} for start placement, and do not introduce one-to-many assignment semantics under a misleading flag name.

\subsection{Global Solver Toggle Contract}
The \texttt{enhanced\_CBS} switch is global. Do not quietly make solver choice branch-specific unless that experiment-design change is intentional and documented. The current design uses one solver family for the whole run so solver behavior remains comparable across branches.

\subsection{Branch-Level Low-Level Guidance Contract}
The new \texttt{true\_static\_shortest\_path\_distance} and \texttt{tight\_time\_horizon} values are branch-local, but they affect solver behavior deeply. If either one changes, keep the propagation consistent across:
\begin{itemize}[leftmargin=2em]
    \item \texttt{master\_config.py},
    \item \texttt{experiments/branch\_specs.py},
    \item \texttt{experiments/study/runtime.py},
    \item the relevant low-level A* modules,
    \item the CBS/ECBS wrappers that call those modules,
    \item branch-header logging and recorded branch metadata.
\end{itemize}

\subsection{Output Contract}
Downstream reading, analysis, or prompting may depend on the current output tree and JSON/CSV file names. Renaming those outputs should be treated as a deliberate interface change. The same applies to the solver metadata fields written into branch specs and run records. The presentation-output tree is now latest-only across runs: each purpose writes back into one stable location such as \texttt{logs/computation/}, \texttt{records/graphs\_and\_data/}, or \texttt{visualizations/}. A newer run intentionally clears and replaces the previous contents for that same purpose, so do not quietly reintroduce accumulating \texttt{execution\_...} folders.

The graphing layer now has a compact-axis contract: the plotted points come from persisted raw MAPF data, and the x-axis tick labels must be the actual agent numbers present in that plotted payload rather than the full current branch domain from \texttt{master\_config.py}. The practical consequence is that graph regeneration should continue to read older saved data without stretching the axis to newly configured but uncomputed values. If this behavior changes, update \texttt{experiments/study/orchestrator.py} and \texttt{experiments/study/plotting.py} together, and document whether the change is still backward compatible with existing raw MAPF stores.

Visualization logging now includes elapsed-time milestones during Pillow frame generation itself, not just before and after the whole visualization stage. Static campus visualization regeneration also reconstructs gray render-only cells from the current campus semantic image instead of relying on persisted raw MAPF payloads, so backward compatibility with older raw stores now depends partly on keeping that image-based reconstruction path intact. If either behavior changes, keep \texttt{experiments/study/visualization.py} aligned with the logger interface in \texttt{experiments/study/io\_utils.py}.

\subsection{Persisted Raw-Data Contract}
The project now stores branch-local raw MAPF data under \texttt{dev/outputs/raw\_mapf\_files/<map\_type>/}. That store is split into a manifest, metadata files, and per-condition subfolders rather than one monolithic pickle. It is reused manually through \texttt{recompute\_MAPF} rather than validated automatically against code or configuration. The loader currently knows how to migrate older branch roots from the previous top-level raw-data folders, so future layout changes should keep backward-compatibility in mind. If compute-stage data shape changes, update both the writer/reader logic and the documentation, and assume older saved layouts may need migration or replacement.

\subsection{Visualization Selection Contract}
The visualization stage no longer flips between one joint-selection mode and one independent-selection mode. Instead, one visualization-only execution now renders both output variants, controlled by \texttt{num\_last\_runs\_to\_visualize\_jointly\_successful} and \texttt{num\_last\_runs\_to\_visualize\_independently\_successful}. If you change how those selections work, update:
\begin{itemize}[leftmargin=2em]
    \item \texttt{master\_config.py},
    \item \texttt{experiments/branch\_specs.py},
    \item \texttt{experiments/study/raw\_data\_store.py} if backward compatibility with saved branch specs matters,
    \item \texttt{experiments/study/visualization.py},
    \item documentation under \texttt{documentation/11\_outputs\_and\_visualization} and \texttt{12\_current\_configuration}.
\end{itemize}

\section{When Adding a New Branch}

A new branch usually requires coordinated updates in at least:
\begin{itemize}[leftmargin=2em]
    \item \texttt{master\_config.py},
    \item \texttt{experiments/branch\_specs.py},
    \item \texttt{experiments/study/preparation.py},
    \item possibly \texttt{visualization.py},
    \item and potentially loader logic under \texttt{inputs/}.
\end{itemize}

\section{When Changing Solver Behavior}

Solver updates now touch more than just the planner implementation. Before changing CBS or ECBS behavior, check whether you also need to update:
\begin{itemize}[leftmargin=2em]
    \item \texttt{master\_config.py} if the user-facing toggle changes,
    \item \texttt{experiments/branch\_specs.py} if metadata recorded for the run changes,
    \item \texttt{experiments/study/runtime.py} if dispatch or result metadata changes,
    \item the low-level guidance helpers if the heuristic or horizon policy changes,
    \item documentation under \texttt{documentation/05\_solver\_behavior}, \texttt{08\_dynamic\_shared\_pipeline}, and \texttt{12\_current\_configuration}.
\end{itemize}

\section{When Changing Sampling Rules}

Sampling logic is branch-sensitive. Before changing it, check:
\begin{itemize}[leftmargin=2em]
    \item whether goals must remain unique or use the target-only \texttt{single} mode,
    \item whether the branch requires individual reachability,
    \item whether the branch expects \texttt{dispersed} or \texttt{clustered} start placement,
    \item whether the branch expects \texttt{dispersed}, \texttt{clustered}, or \texttt{single} goal placement,
    \item whether the branch requires starts and goals to occupy different campus zones,
    \item whether the allowed start and goal vertices come from an image-semantic mask,
    \item whether the branch should enforce dispersed 8-neighbor separation or clustered placement, and if clustered placement is active whether the project-wide \texttt{compact\_clustering} toggle should imply compact adjacency or connected one-cell-gap spacing.
\end{itemize}

\section{A Good Mental Rule}

A safe update usually preserves the separation:
\[
\text{configuration} \rightarrow \text{normalized branch spec} \rightarrow
\text{preparation} \rightarrow \text{solver execution} \rightarrow
\text{aggregation/output}.
\]
If a change smears all of those layers together, the project becomes much harder to maintain.
