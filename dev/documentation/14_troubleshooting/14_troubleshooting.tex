\section{Campus Zones Not Detected}

If a campus run reports something that implies zero usable zones, such as a log with \texttt{zone\_cells=0}, check the source image before changing the code. The current campus loader expects the designated zone colors to be present in the actual image asset. Also confirm that the branch/image pairing and the \texttt{narrow\_lanes} settings in \texttt{master\_config.py} still point to the intended lane variant: \texttt{static\_campus\_area\_1} should select one of the \texttt{campus\_area\_1\_*\_lanes.png} files and \texttt{dynamic\_campus\_area\_2} should select one of the \texttt{campus\_area\_2\_*\_lanes.png} files.

\section{Clustered Sampling Keeps Failing}

If a branch repeatedly fails during assignment preparation, inspect the interaction among:
\begin{itemize}[leftmargin=2em]
    \item requested agent count,
    \item whether the branch is using dispersed separation or directly adjacent cluster mode,
    \item cluster mode,
    \item zone restriction,
    \item reachability filtering.
\end{itemize}

A cluster request is intentionally loose, but it can still fail if one zone is too narrow or too fragmented to fit the requested count under the active cluster style. With \texttt{compact\_clustering=True}, the cluster must fit as one directly adjacent component. With \texttt{compact\_clustering=False}, the cluster must still stay connected while keeping one empty cell of separation in all 8 directions.

\section{Distinct-Zone Campus Sampling Fails}

In campus \texttt{distinct\_campus\_zones} mode, the code must find:
\begin{itemize}[leftmargin=2em]
    \item enough valid start vertices in one zone,
    \item enough valid goal vertices in a different zone,
    \item a one-to-one reachable matching between those two sets when reachability is required.
\end{itemize}

If any of those three conditions fails, the run configuration is rejected and a new one is sampled.

\section{Campus Visualization Looks Open but Solver Treats It as Blocked}

Gray campus regions may be recorded as \texttt{visually\_free\_vertices} for rendering purposes. That does not make them solver-traversable. If a visualization looks more open than the solver behavior suggests, check whether the region is semantically gray rather than truly traversable.

\section{Progress Lines Appear in a Burst}

If the solver seems silent for a long time and then prints many progress lines at once, the most likely cause was stdout buffering. The current logger now flushes each line immediately. If this symptom returns, inspect any new logging path that bypasses \texttt{ExperimentLogger.log()} or writes through a buffered wrapper without flushing.
